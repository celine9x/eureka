Figma mobile checklist
File setup
Page names are clear and consistent.

Frames are organized by flow or feature.

Screens use consistent device sizes.

Components, variants, and styles are used instead of detached one-off elements.

Layers and frames are named clearly for handoff.

Design system
Colors use shared styles or variables.

Text uses shared text styles.

Spacing follows a consistent scale.

Buttons, fields, cards, and navigation use reusable components.

States exist for default, pressed, disabled, loading, and error where relevant.

Layout review
Each screen has one clear primary action.

Visual hierarchy is obvious at first glance.

Content is aligned consistently.

Spacing between sections is even and intentional.

Layout still works on smaller mobile screens.

Buttons and tap targets
All tappable elements meet minimum mobile target size.

Android-style targets are at least 48 Ã— 48.

Icon-only buttons still have a full touch area around the icon.

Typography
Body text is readable on mobile.

Small text does not go below 12 px, and important text is larger than that when possible.

Text styles are limited and used consistently.

Line height supports readability.

Text is never centered in long paragraphs unless there is a strong reason.

Color and contrast
Text contrast meets accessibility expectations.

Information is not conveyed by color alone.

Disabled, error, success, and warning states are visually distinct.

Links, buttons, and selected states are still clear in grayscale or color-blind simulation.

Background and foreground combinations remain readable across all states.

Forms
Every field has a visible label.

Required and optional fields are clear.

Placeholder text is not used as the only label.

Input states exist for default, focus, filled, error, and disabled.

Error messages explain what is wrong and how to fix it.

States and feedback
Loading states are designed.

Empty states are designed.

Error states are designed.

Success or confirmation feedback is designed.

Destructive actions include confirmation patterns when needed.

Navigation and flow
Back behavior is clear.

Navigation patterns are consistent across screens.

Bottom nav, tabs, drawers, or menus are used consistently.

The user can always tell where they are.

Important flows are connected in prototype mode for review.

Accessibility checks
Reading order is logical.

Focus order is considered for keyboard and assistive tech review.

Images and icons that need text alternatives are identified.

Touch targets are validated.

Motion, blinking, or animation is not excessive.

Handoff readiness
Components are published or ready for inspection.

Spacing, size, radius, and color values are consistent.

Edge cases are included, not just happy paths.

Notes are added for complex interactions.

Developers can inspect the file without guessing intent.
